## 5. 外部隐藏测试

外部测试共 13 个，测试源码对三个候选完全相同。

| 候选 | 通过 | 失败 |
|---|---:|---|
| mini-swe-agent | **9 / 13** | 注册不要求验证码；确认密码不一致仍注册；负数出库被接受；两个并发草稿可共同超额占用库存 |
| DeepSeek Harness | **12 / 13** | 确认密码不一致仍注册 |
| Pi | **12 / 13** | 负数出库被接受 |

### 行为测试覆盖

- 缺失、伪造或格式错误的令牌。
- JWT 自称管理员但数据库实际角色较低。
- 已禁用或不存在的用户。
- 注册验证码、确认密码、角色批量赋值、密码泄漏。
- 管理员修改角色后权限是否实时生效。
- 重复确认出库、非草稿编辑、负数数量、重复物料合并校验。
- 两个并发订单对同一库存的超额占用。

严重性判断：Pi 的负数出库属于库存数据完整性缺陷；DSH 的确认密码缺失属于注册校验缺陷。两者都必须修，但前者对核心业务数据风险更高。

## 6. 真实运行与页面验收

所有候选均使用同一 Java、Maven、Node 环境和独立 H2 数据库，按顺序启动，未同时占用系统资源。

### mini-swe-agent

- 后端与前端均能启动，具体业务路由可以加载。
- 访问系统根路径 `/` 稳定触发 Vue Router 无限重定向，最终白屏；这会影响用户首次打开系统。
- 直接访问 `/login` 可显示登录页，直接访问 `/inbound/purchase` 可进入后台。
- 角色权限页角色列表为空，无法选择和编辑既有角色。
- 页面只有菜单级权限树，没有需求中的按钮级权限和数据范围配置。
- 运行期间后端未产生异常日志，但这不能抵消前端入口故障。

### DeepSeek Harness

- 根路径正常重定向登录页，登录后后台正常加载。
- 采购入库增加了物料、时间筛选及批量通过/拒绝。
- 库存菜单包含 CIS 同步和物料管理。
- 角色权限页具有角色列表、数据范围、菜单权限和按钮权限，功能面最贴近需求。
- 抽查期间后端无异常日志。
- 注册页面有验证码与确认密码，但后端实际没有校验确认密码。

### Pi

- 根路径、登录和后台菜单正常；库存、预警扫描、报表、用户、角色权限页均可加载。
- 角色权限页有数据范围和菜单树，默认测试账号/角色初始化完整。
- “钉钉登录”按钮前端调用错误：调用方传字符串，API 封装把它当查询参数对象，导致后端收不到必填 `redirectUri`，页面只显示请求失败。
- 抽查期间后端无异常日志。
- 记住密码仅使用 XOR + Base64 混淆，不是需求所称的真正加密。

## 7. 各候选主要优缺点

### DeepSeek Harness

优点：核心库存隐藏测试全过；权限表面最完整；CIS、物料管理、按钮权限、数据范围等需求覆盖最好；产物紧凑。  
缺点：确认密码后端漏检；完成说明存在不实陈述；运行过程中把原 Git worktree 转成了独立仓库并丢失基线祖先关系，破坏了评测隔离边界，虽然代码结果可恢复，但必须扣过程分。

### Pi

优点：40 个自带测试为三者最多；安全、权限、BOM、库存预警的测试组织最好；代码和文档相对一致；后台可用。  
缺点：负数出库会破坏库存数据；钉钉登录前端参数接错；轨迹文件约 788 MiB，整个结果目录约 794 MiB，远高于 mini 的 4.3 MiB 和 DSH 的 2.7 MiB，不适合原样保存或上传 GitHub。

### mini-swe-agent

优点：完成了可构建的全栈改造；产物小；直接业务路由及多数页面可加载。  
缺点：4 个关键隐藏测试失败；根路径白屏；角色列表为空；权限颗粒度不足；自带测试数量少且存在测试名与行为相反的问题。它更像一次“广泛补齐”，但缺少可靠的收尾验收。

## 8. 共同限制

- 钉钉与 CIS 没有真实企业环境，验收只认可可配置适配器或确定性 mock，不声称真实集成已通过。
- 三个版本都只在 H2 MySQL 兼容模式验证，没有连接真实 MySQL 8 做回归。
- 三个版本都没有前端自动化测试。
- 三个版本都保留了用于本地评测的 JWT 默认密钥；生产部署必须强制从环境变量注入并禁止默认值。
- `npm audit` 尚未执行，因为该操作会把依赖清单元数据发送到 npm 服务；只有得到用户明确授权后才运行。这不影响当前源码行为排名，但属于尚未完成的供应链检查。

## 9. 建议的最终代码路线

1. 以 DeepSeek Harness 结果作为第一候选底稿。
2. 合并前必须修复确认密码后端校验，并补回归测试。
3. 从 Pi 借鉴其更完整的测试结构、默认数据初始化以及文档化方式。
4. 为前端增加最少一组 Playwright 或 Vitest 测试：根路径、登录、主菜单、钉钉按钮参数、角色权限页。
5. 在真实 MySQL 8 上重跑入库、出库、并发锁定与导出测试。
6. 外部钉钉/CIS 继续保留 mock；有真实测试环境后再单独验收，不把“代码存在”写成“集成通过”。

## 10. GitHub 发布原则

可以发布整个评测项目，但建议先创建私有仓库审阅，再决定是否公开。公开仓库应包含：

- 脱敏需求、固定基线身份、三个 harness 的版本与配置。
- 统一任务文本、评分规则、隐藏测试源码或公开版测试、构建脚本、最终报告。
- 三个候选的精简补丁、提交列表和摘要。
- 明确的环境限制和可复现步骤。

不要上传：API Key、`.env`、数据库备份、公司仍有效的信息、完整 788 MiB Pi 轨迹、`node_modules`、Maven 缓存和构建产物。若公开代码本身，需再次确认其中没有第三方许可证、个人信息、真实内网地址或仍有效凭据。
