# 搭建与评测过程中的经验

## WSL 与 D 盘

- WSL 本身可以放在 C 盘；项目和缓存放 D 盘能减少系统盘压力。
- `/mnt/d` 默认挂载权限可能使 Git 无法创建锁文件。启用 drvfs metadata 后，chmod 与 Git 才能正常工作。
- Node 项目放在 `/mnt/d` 时，大量小文件 I/O 可能非常慢。Pi 在 D 盘安装后启动超时，改为 Linux 文件系统安装即可在约 1 秒内启动。

## 网络与代理

- Windows 的 localhost 代理不会自动在 WSL NAT 模式中生效。
- GitHub 大仓库克隆时，浅克隆可显著减少对象数量；但浅克隆不包含完整历史，需要在研究贡献历史时再补全。
- 镜像源适合 npm/pnpm 包，不能假设任意 GitHub 仓库都有可信镜像。

## harness 与工作区

- harness 的安装目录与它实际修改的工作区是两回事。启动命令所在目录通常决定 Agent 能看到和操作哪个代码库。
- 评测必须为每个 Agent 使用独立工作区，不能让后一个 Agent 看到前一个的结果。
- 工作区之外还要保存补丁、提交、任务文本、配置和版本身份，否则结果很难复现。

## 不要完全相信 Agent 的总结

- 自带测试通过只能证明它测试了自己想到的内容。
- 文档可能声称功能完成，但实现仍缺少后端校验。
- 页面构建成功不代表根路由和按钮参数正确。
- 必须使用 Agent 未见过的外部测试，并实际启动页面。

## 过程本身也是评测对象

- DeepSeek Harness 结果代码很好，但运行过程把链接 worktree 变成了独立仓库，破坏了原基线祖先关系。
- Pi 的结果完整，但轨迹达到约 788 MiB，给保存、审查和发布带来明显成本。
- mini-swe-agent 的产物最紧凑，但关键缺陷收尾不足。
