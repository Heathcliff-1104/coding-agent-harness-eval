# 评测方法

## 研究问题

1. 同一个 DeepSeek 模型在不同 coding-agent harness 中，能否完成同一套真实全栈需求？
2. 不同工作流、子 Agent 和上下文组织方式会怎样影响功能覆盖、正确性与过程质量？
3. Agent 的自带测试和最终总结，与外部验收之间有多大差距？

## 控制变量

- 相同脱敏基线提交：`3bf29e545f9461128ea4d3c589f501ad374f59c1`。
- 相同需求文档。
- 相同模型：`deepseek/deepseek-v4-flash`。
- 相同本地 Java、Maven、Node 和 WSL 环境。
- 允许网络访问。
- 三次运行顺序执行，不并发争抢本地资源。
- 钉钉与 CIS 允许确定性 mock，因为没有真实企业测试环境。

## 刻意不统一的变量

本实验不是严格的等 token 模型评测。为保留 harness 的设计哲学，下列部分使用各自原生方式：

- mini-swe-agent 以单 Agent 长任务运行。
- DeepSeek Harness 使用原生 headless profile、工作流和子 Agent。
- Pi 使用官方 subagent 示例，仅把子 Agent 模型字段适配为 DeepSeek。

因此，结果应解释为“固定环境下的整体工具使用效果”，而不是纯模型能力排名。

## 执行阶段

1. 将需求与源代码脱敏并建立固定 Git 基线。
2. 为每个 harness 创建隔离工作区。
3. 提供相同目标：调查缺失功能、持续实现、运行测试、记录限制。
4. 运行结束后冻结提交、补丁、任务、配置与轨迹身份。
5. 从冻结结果创建独立验收副本。
6. 执行干净构建、自带测试和 API 合同检查。
7. 注入相同的外部验收测试。
8. 顺序启动前后端，实际检查登录与核心业务页面。
9. 按预先定义的五维评分框架打分。

## 评分框架

| 维度 | 权重 |
|---|---:|
| 需求完成度 | 45 |
| 正确性与安全 | 25 |
| 构建与测试工程 | 15 |
| 真实页面可用性 | 10 |
| 过程与可复现性 | 5 |

详细分项与扣分证据见 `docs/acceptance-report.md`。

## 外部验收测试

公开后的测试不再是“隐藏测试”，但在三个 Agent 运行时，它们未包含在任务上下文中。测试覆盖：

- 令牌伪造、数据库实时角色、禁用用户。
- 注册验证码、确认密码、角色批量赋值与密码泄漏。
- 角色变化实时生效。
- 重复确认、非草稿编辑、负数数量、重复物料。
- 两个并发订单对同一库存的超额占用。

## 局限性

- 只有一个真实项目，不能代表所有代码库。
- 没有等 token、等费用或等工具调用。
- 没有真实 MySQL 8、钉钉与 CIS 环境。
- 页面验收为关键路径抽查，不是完整端到端自动化套件。
- 评分含有工程判断；因此公开权重、原始测试和证据，允许读者重新加权。
