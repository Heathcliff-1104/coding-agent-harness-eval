# 项目背景与初衷

## 从“会用模型”到“理解 harness”

这个项目开始于一个很朴素的目标：我想真正跑一遍 coding-agent harness，而不只是调用一次模型 API。

最初我对 Agent 开发几乎没有经验。安装 WSL、处理 Windows 与 Linux 文件权限、理解 worktree、配置模型、观察轨迹、区分模型与 harness 的职责，这些都属于学习过程的一部分。因此，本仓库既记录最终代码结果，也记录搭建与验收过程中出现的问题。

## 为什么使用真实旧项目

相比专门设计的小题目，一个未完成的真实业务系统更容易暴露 Agent 的差异：

- 它没有清晰到可以机械照抄的单一 issue；
- 前后端需要共同修改；
- 需求包含权限、库存状态、并发、外部系统与报表；
- “页面看起来完成”不等于业务不变量正确；
- Agent 必须自己决定调查范围、任务拆分和验证方式。

所用项目为本人有权使用的历史代码。发布版本移除了环境信息，并把项目名称与个人称谓改为通用表述。

## 为什么选择这三个 harness

- **mini-swe-agent**：结构小、容易理解，适合作为第一次完整跑通 harness 的入口。
- **DeepSeek Harness**：强调一切插件化、工作流与子 Agent，适合观察并行调查和任务编排。
- **Pi**：核心简洁、扩展能力强；官方 subagent 示例提供 scout、planner、worker、reviewer 等角色。

我没有试图把三者改造成同一种架构。实验希望观察的正是：在相同模型与同一项目下，不同 harness 的原生哲学会怎样影响最终结果。

## 最终目标

这个仓库希望给后来者提供三种价值：

1. 一套从安装、运行到独立验收的真实路径。
2. 一份可以质疑和复查的比较结果，而不只是主观体验。
3. 一些关于 Agent 评测设计的教训：冻结结果、隐藏测试、真实页面检查、过程审计和敏感信息治理同样重要。
